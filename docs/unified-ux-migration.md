# Unified UI/UX Migration Guide

Use this guide with issue #2559 when planning or implementing new UI/UX work. It is intentionally lightweight: do not create an exhaustive feature register before building. Add workflow notes only when a workflow is actively planned, rebuilt, bridged, deferred, combined, or retired. Use the [current-state notes guide](unified-ux-current-state.md) with issue #2558 when a v1 workflow needs existing v0 behavior documented.

The production v1 validation policy is defined in [V1 Data Validation and Status Rules](v1-data-validation-rules.md). Update that document, the rule catalog, presentation copy, and tests together whenever v1 validation behavior changes.

## Source Layout

- `src/app/v0/` contains the current production UI. Keep legacy routes and v0-only presentation behavior here.
- `src/app/v1/` contains the opt-in production unified workspace reached through `/v1` on `unified-ux`.
- `src/app/ux-prototypes/` contains P1 prototype reference material reached through `/p1` on `unified-ux`. Prototype code can inform v1, but production v1 should not depend on prototype-only components unless they are deliberately promoted.
- `src/app/shared/` contains version-neutral helpers and contracts; import it with `@shared/*`.
- `src/app/v0/shared/` contains legacy reusable UI that is shared only inside v0; import it with `@v0/shared/*`.
- `src/app/data/` contains shared data contracts: account workspace, IndexedDB, backups, persisted models, and migrations.
- `src/app/domain/` contains deterministic calculations and domain helpers.
- `src/app/platform/` contains Electron services, Web Worker wrappers/contracts, analytics, and other runtime integration boundaries.

Current boundary examples:

- Root shared keeps form, fuel, vehicle, date/helper service, router-guard, notification-state, and analysis-calculation contracts.
- v0 shared owns legacy helper pipes, spinners, labels, table/dropdown helpers, meter content, data-quality displays, analysis presentation widgets, report widgets, settings/help UI, and similar presentation bundles.
- Meter charge option types/constants live in `src/app/data/models/meter-charges-options.ts` because they are used by persisted models, migrations, exports, and v0 forms.

## Protected Contracts

Do not change these contracts as incidental UI migration work:

- IndexedDB schemas, store names, indexes, migrations, and record defaults.
- JSON backup shape, data-version handling, import/export compatibility, and GUID remapping.
- Spreadsheet imports/exports, report exports, and generated report values.
- Calculation inputs, outputs, units, rounding, and aggregation semantics.
- Web Worker request, response, error, and structured-clone payloads.
- Electron IPC channels, preload allowlist, context isolation, and desktop file behavior.
- Account workspace publication, selection repair, committed revision, and command-boundary behavior.
- Persisted model identities, especially GUID relationships versus local numeric IndexedDB ids.

## Workflow Decision Note

When a workflow enters v1 planning or implementation, record only the decisions needed for that workflow:

- **Workflow:** Name the workflow and its existing v0 entry point.
- **Decision:** Rebuild in v1, share logic, temporarily link to v0, combine with another workflow, defer, or retire.
- **Parity:** Name the user-visible behaviors that must match v0.
- **Shared contracts:** List any data, domain, file, Worker, Electron, or report contracts touched.
- **Tests:** Name the focused unit, browser, Electron, or manual checks required.

If the workflow needs current-state detail, add a short current-state note using the template in the [current-state notes guide](unified-ux-current-state.md). Do not create a full application inventory as a prerequisite for v1 work.

- **Existing v0 entry point:** `/data-management/:account/import-data/upload-files` and its template, general-workbook, and footprint child routes.

- **Tests:** Parser compatibility and round trip; v1 queue, step, route, validation, and navigation protection; browser File API, IndexedDB add/update, GUID relationships, single publication, and rollback.

### Single-Facility Navigation

- **Decision:** Valid single-facility companies (`isSingleFacilityCompany` with exactly one facility) use the facility as the root of Data and Analysis. Their sidebar shows the company name once in the top label with a facility icon in every section, without a separate facility row or dropdown. Data and Analysis have no account return or account breadcrumb; workbench facility breadcrumbs return to the matching facility inventory.
- **Routes:** Account Data bookmarks redirect to the matching facility inventory; Facilities and the default Portfolio destination open Meters. Account Analysis retains its paired-analysis redirects. These rules apply to child navigation from an already-open account workspace as well as direct entry.
- **Exceptions:** Account Reports and Upload remain explicitly reachable. Upload keeps its facility selection and return information. Invalid single-facility states retain recovery navigation, and conversion to a portfolio restores account/facility navigation.
- **Shared contracts:** No persisted models, calculation inputs, file formats, or Electron boundaries change.
- **Tests:** Focused sidebar, breadcrumb, return-control, and real-router transition specs; application type-check and production web build.

### V1 Data Validation, Status, and Todo Workflow

- **Workflow:** Account-wide v1 data validation, Home status summaries, support-panel Todos, meter cards, Readings alerts, and the selected-meter Quality Report.

- **Tests:** Table-driven rule/catalog tests, v1 consumer specs, and a browser Worker test that rejects superseded account revisions. Run the validation planner, fast and browser suites, app type-check, and production web build.

### Data Validation Settings Workflow

- **Workflow:** Account and facility Settings > Data Validation, replacing Staleness navigation. Existing `settings/staleness` links redirect to `settings/data-validation`.
- **Decision:** Separate staleness and expected-range sections with independent facility inheritance, account-copy confirmations, and serialized autosave. Navigation is blocked while saves are queued or in progress. Failed drafts can be retried, reverted, or explicitly discarded; reverting all edits to stored values clears the save error. Once persistence commits, a failed workspace or catalog refresh invalidates save deduplication until a successful save reconciles the preference. One expected-range switch controls consumption, cost, and predictor status warnings; statistical Quality Report details remain available.
- **Shared contracts:** Optional account/facility `expectedRangeSettings` defaults to enabled, with facilities inheriting unless `useAccountSettings` is explicitly false. Older records and backups require no rewrite or data-version change. JSON backups retain the preference; spreadsheet formats, v0 checks, formulas, and Worker contracts remain unchanged. Single-facility account/facility synchronization commits atomically through a compound command handler.
- **Tests:** Defaults, inheritance, autosave/retry/serialization, route compatibility, portfolio propagation, report fallback alerts, JSON round trips, and native IndexedDB commit/rollback/reopen. Run the validation planner, fast/browser suites, app type-check, and production web build.

### Production v1 Data workbench architecture norms

- **Collection versus route ownership:** A feature workspace service owns account- or facility-scoped collections, browse-card projections, grouped-resource projections, write availability, and pending state. A route-scoped context owns the selected resource, its child records, findings, active-tab state, and feature-specific navigation. Route contexts read `ActivatedRoute.paramMap` so direct links and in-place parameter changes resolve through the same path. They expose a missing-resource state instead of retaining a stale selection.
- **Canonical routes:** Route guards redirect resource variants before constructing the wrong workbench. Weather predictors always use the Weather station workbench; standard Predictor Settings and Readings do not retain unreachable Weather branches. Existing `/v1` URL shapes remain stable.
- **Child-state ownership:** A child component owns interaction state that has no meaning outside that child, including disclosure, editor dirtiness, focus return, local sorting, and pagination. Parents pass domain data or capabilities only when the child is intentionally reusable. Do not add inputs and outputs merely to mirror child state in a route container.
- **Inputs and outputs:** Reusable editors, tables, selectors, and presentational cards use explicit inputs and semantic intent outputs. Route-bound reports and workbench panels inject their route context instead of accepting optional entity inputs, navigation outputs, or fallback services. Shared resource switchers emit only the selected resource identifier; feature contexts continue to own route construction and navigation.
- **Shared presentation boundaries:** Use the shared Data workbench tabs, resource switcher, collapsible facts, resource browse card, confirmation dialog, and focus-management primitives before creating feature copies. Shared components own interaction semantics, keyboard behavior, and presentation state; feature wrappers own data shaping, permissions, persistence commands, and navigation.
- **Confirmation modals:** Confirmation content opened from routed workspace components must live in an `ng-template` and be attached to the shell-level outlet with `ModalPortalService` and `TemplatePortal`. Compose the template with `ConfirmationDialogComponent`, providing a unique title ID, a specific cancellation label, an action label, the matching action icon, and the appropriate shared button tone. The component already owns the `v1-modal-layer`, backdrop, focus trap, Escape handling, header, body, footer, responsive sizing, theme surface, and corner settings. Feature code owns only the pending action, explanatory content, disabled/busy state, and confirm/cancel commands. Always hide the portal after confirm, cancel, and component destruction. Do not recreate `v1-modal*` markup or add feature-level backdrop, dialog, or `z-index` rules: the workspace is an isolated stacking context, and only the shell outlet reliably paints above the sticky header and navigation.
- **CSS reuse:** Put repeated dashboard grids, toolbars, card hosts, sticky headers, tabs, and dialog structure in shared components or semantic v1 classes. Feature styles describe only feature-specific layout or appearance. Workbench sections retain connected borders, square outer corners, and no vertical gaps.
- **Alerts and month previews:** Shared v1 alerts use opaque, severity-tinted theme surfaces.
