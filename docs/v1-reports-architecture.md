# V1 report architecture

The Reports feature lives under [`src/app/v1/reports`](../src/app/v1/reports). Its directly routed unified inventory owns browsing and lifecycle actions. Account/facility route hosts resolve ownership and navigation; a shared workbench owns the active report session and stage presentation. Valid single-facility accounts keep the combined Reports inventory so account-backed reports remain accessible. Individual report migrations supply their typed editor, applicable checks, calculations, and in-app content. Better Plants is the first implemented account report; facility Analysis supplies the corresponding direct-facility setup, checks, and continuous in-app report. See [#2804](https://github.com/ORNL-AMO/VERIFI/issues/2804).

Account report Setup ends with a Delete report action using the existing report deletion command and shell confirmation portal. Confirmation pauses autosave and permits deletion of incomplete drafts. Cancel or failure preserves the draft; only a committed deletion discards it and returns to the account Reports dashboard. The workbench owns the deletion coordinator so removing the selected report can unmount Setup without interrupting the return navigation. Analyses, source data, and other reports remain unchanged.

## Ownership and extension pattern

- `catalog/` owns static, scope-qualified report metadata: labels, icons, Other Impacts availability, applicable stages, implemented content, and analysis-return support. The [catalog](../src/app/v1/reports/catalog/report-catalog.ts) is exhaustive over the existing saved report types; it does not own calculations, validation policy, or persistence commands. Account Analysis and facility Analysis remain distinct definitions.
- `inventory/` owns browsing projections and lifecycle presentation. `account/` and `facility/` own route adapters, contexts, commands, and explicit pending-format fallbacks. Keep each implemented report's editor, settings, coordinator, projections, and stage components together in its report feature folder.
- `shared/` contains report capabilities grouped by purpose: workbench, editing, analysis selection/inspection/checks, calculation coordination, document presentation, and output actions. Analysis tables, charts, and column presentation used outside Reports stay under `v1/shared/analysis-results/`.
- The shared [workbench controller](../src/app/v1/reports/shared/workbench/report-workbench.controller.ts) mounts one feature runtime for an immutable account/facility/report GUID identity. A typed feature definition supplies its providers and stage components. Setup, Data Checks, and Report replace only the stage view; the editor, checks, and current result survive stage navigation. A different report identity destroys the mounted stage and its feature injector, cancelling work and releasing subscriptions before the next runtime starts.
- Scope hosts supply presentation, canonical links, ownership, and feature definitions through `ReportHostAdapter`. `ReportRuntime` supplies the typed editor, optional checks/review capability, and footer capabilities. The shared shell/controller owns setup gating, Continue/Back, leave flushing, unload protection, and the stage projection published to the sidebar. Feature components consume prepared state and typed commands.
- Both scope routes save pending edits before stage changes, report switching, and exits. Invalid or failed saves preserve the current route, session, and draft. Editors hydrate silently before a stage's first render so opening a report never creates an autosave command.
- Shared report stage surfaces use the current appearance radius for their bottom outer corners while preserving connected section borders.
- Account and facility report Setup share [`ReportAnalysisSelectionComponent`](../src/app/v1/reports/shared/analysis-selection/report-analysis-selection.component.ts) for typed category/baseline filters, selection cards, current status badges, and inspection actions. Scope-specific adapters supply eligible choices and retain selection, inspection, and save ownership. The shared top section places report information beside reporting-period controls and stacks them at narrow widths. Required year and analysis fields have visible and accessible required indicators.
- Reuse `ReportAutosaveController` for scheduling and protection. A feature editor owns a typed draft and translates only explicitly edited fields into a setup command. Handlers merge with the latest durable record and publish the full affected-record patch after commit.
- Keep input preparation and deterministic checks/calculations under `domain/reports`; platform owns Worker messages, teardown, and SHA-256 hashing. `AnalysisReportCalculationService` supplies the existing two-minute Worker timeout and the synchronous fallback.
- A report-session coordinator owns demand, current results, errors, and retry. Shared report state vocabulary and form-surface CSS live under the Reports feature. Components render prepared values rather than starting Workers or querying repositories.
- Reuse `ReportResultController` for calculation cancellation, one-result caching, errors, retry, and immediate stale-result suppression. Report adapters retain input preparation, content keys, period policy, review gates, and response validation. `ReportAnalysisInspectionController` shares keyed inspection, demand, selection, and save-before-analysis navigation; scope adapters retain eligibility, selection commands, and return origins.
- Analysis and report column controls/projections derive from the pure shared result-column catalog. Surface adapters retain existing labels/order, predictor selections, fiscal labels, baseline restrictions, and transition masking; sharing column metadata must not silently change either surface's values.
- Separate pure presentation projections from rendering. Better Plants consumes the existing `BetterPlantsSummary` contract and builds form rows without rounding calculated values. Future print/file adapters can consume those results separately from the DOM.
- Resolve report identity icons through the catalog-backed [`reportIcon`](../src/app/v1/reports/catalog/report-icons.ts) lookup. It maps account and facility types separately and falls back to the existing page icon until a custom design is available. Cards, sidebars, workbench titles/switchers/stages, and analysis linked-report rows share this presentation metadata; icon names are never persisted. Follow the [custom-icon guide](../src/app/v1/shared/icons/README.md#report-icons) to add another report design.

When adding another report:

1. Update its scope-qualified catalog entry, including content readiness and applicable capabilities.
2. Create its typed editor, settings, coordinator, projections, and stage components in the owning report folder. Keep report-specific options and period rules there.
3. Declare/import the presentation in its owning NgModule, import the shared capabilities it uses, and register its typed providers/stage definition with the account or facility host.
4. Supply the typed setup-command and deterministic-input adapters it needs. Preserve durable model, receipt, Worker, and output contracts; update their owning layers explicitly if the report requires a new contract.
5. Cover its setup/check/report journey and the shared lifetime/guard contracts. Reuse shared capabilities without adding report-type branches to the workbench shell; unmigrated types retain their explicit placeholders. Add common capabilities only when an implemented report needs them.

## Data flow and calculation lifetime

One committed account workspace snapshot supplies the selected account analysis, owned facilities and facility analyses, transitive banking dependencies, meter readings, and relevant predictor inputs. Single-facility reports preserve their saved hidden account-analysis GUID while resolving the underlying facility analysis as the review owner. Reading a report never creates or repairs pairs; use the existing explicit link-selection/refresh command.

Setup computes review freshness and can reuse cached checks without starting a checks or report Worker. Better Plants Data Checks requests model validation only for the selected report year, independently of **Include all years**. Report generation starts only after that year's current checks are clean or its matching review receipt is available, and current workspace/report validation permits calculation. Direct Report entry enforces the same selected-year gate. All-year output still runs newest first, excludes the baseline itself, and is bounded by the loaded meter history. Changing output-year coverage cancels stale report work and immediately hides its pages without invalidating current selected-year checks; changing the selected report year invalidates both checks completion and displayed pages.

Setup's analysis inspection buttons reuse the account and facility Analysis inspectors and their demand-driven outcome coordinator. Only the inspected analysis requests outcome results, and closing the slideout cancels that demand. Inspection does not change the report link; **Select for report** updates the existing typed draft and uses normal autosave. Account and facility active-reporting selections remain independent.

The shared detail status box contains validation findings and suppresses stale findings while checks are pending or unavailable. Account inspection reuses the Select Facility Items candidate projection for status, group methods, and Data Through, alongside saved modification dates and the summary card's valid/total selection count. Tables adapt to narrow slideouts without horizontal scrolling. Shared linked-item rows identify report types with icons and preserve analysis and banking dependency identities. These views read the workspace without requesting additional result Workers or changing selections.

**Go To Analysis** saves pending report edits and opens the inspected analysis without selecting it. A GUID-based report origin supplies **Return to Report** in both analysis workbench headers. The route-scoped [return service](../src/app/v1/reports/shared/analysis-inspection/report-analysis-return.service.ts) revalidates the owning account and available report, carries validated origin query parameters through stage links, footer navigation, result/group tabs, prerequisite redirects, and account-to-facility drill-ins. Reloaded analysis URLs therefore retain the same report return and read-only entry behavior. Returns save pending analysis edits and use canonical report Setup routes and the existing navigation guards. Missing or unavailable reports suppress the return action. Report-origin facility entry validates the target owner and skips automatic hidden-pair repair, including for an inspected analysis that is not selected for the report.

Analysis selection filters narrow the cards by category and baseline year without changing the selected analysis or saving report edits. The type filter appears only when the account contains both energy and water categories. Filters reset when switching reports, and a selected analysis hidden by the filters remains linked and is identified above the cards.

The coordinator retains only its current checks and report results. Changes to account/report identity, readiness, operation, or checked content cancel obsolete work. Report calculation freshness additionally covers all prepared meter inputs, including additional water outside the intensity calculation, and facility manufacturing classification. The coordinator uses fresh prepared report inputs independently of cached checks, so those report-only changes refresh values without invalidating a current analysis review. A synchronous state projection hides old results before Observable scheduling can publish another result. Changes to names or report notes reproject presentation without regenerating calculations. Hashing participates in Angular pending-task tracking; Worker unsubscription, error, timeout, and completion terminate the Worker.

## Explicit shared analysis review

Clean checks complete automatically without writing a receipt. Visiting Data Checks never acknowledges issues: users check the shared footer acknowledgment beside Continue to explicitly save review. Model issues at any severity, failed validation flags (even when legacy notes are absent), and report warnings require acknowledgment; informational findings alone do not. Critical model issues, blocking report/analysis findings, empty results, and missing requested periods prevent completion and acknowledgment. Continue remains disabled until completion; pending and completed status is shared by the header, stage indicator, and footer. A report that still requires review shows a Data Checks action instead of values.

Account and facility analyses have an optional `dataCheckReviews` array. Each receipt records the checks version, report year, SHA-256 input fingerprint, and confirmation timestamp. One receipt is retained per checks version/year. Account-backed reports store receipts on the account analysis for portfolios, or the underlying facility analysis for single-facility workspaces. Direct facility reports always store receipts on their facility analysis. Matching reports share it, independently of their names, notes, or content visibility options. Better Plants acknowledgment covers only the selected report year, including when earlier report pages are displayed. Existing historical receipts remain compatible and are preserved, but cannot substitute for the selected year's receipt.

The fingerprint includes the review owner, reporting year, baseline, effective calculation settings, selected facility/group analyses and models, banking dependencies, relevant meters/readings, and predictor inputs. String `id` values on analysis/model predictors are GUID references and remain part of the fingerprint; only numeric local `id` keys are excluded. It also excludes receipt metadata, names, contact details, and display metadata. GUID collections are canonicalized; coefficient and predictor ordering is preserved. Unused regression candidates and meters outside the included/banking groups do not invalidate review. Older receipts that omitted predictor references become stale naturally when the current content is hashed; their stored shape remains compatible.

Acknowledgment computes and validates the displayed checks before opening an IndexedDB transaction. The transaction rereads the complete dependency set, synchronously compares its canonical content with the displayed content, merges receipts into the latest analysis, and commits atomically. Asynchronous hashing never occurs inside a native IndexedDB transaction. A changed dependency or failed write prevents confirmation and publication.

Absent receipts mean unreviewed; completion can still be established by current clean check results. This optional addition needs neither a record backfill nor an IndexedDB schema/data-version increment. Backups can carry the optional metadata; import clears it after GUID remapping. Analysis copies clear receipts. Copying a report can reuse review of its unchanged analysis. Legacy `isAnalysisVisited` and `dataCheckedDate` remain separate and are not advanced by report navigation or acknowledgment.

## Reusing analysis checks in another report

- Construct `AnalysisChecksController` from `shared/analysis-checks/` in the active report runtime's injection context, as with `ReportAutosaveController` from `shared/editing/`. Keep one instance per report session; do not provide a global controller or create another instance for each routed stage.
- Supply a reactive `AnalysisChecksRequest`: a stable report/context key (unchanged during pending writes), readiness or error, prepared `AnalysisReportInputs`, requested validation years, canonical-owner receipts, and current blocking/warning findings. Validation years can differ from generated output years; the report adapter owns that policy. Demand is `freshness` in Setup, `checks` for the Data Checks page, and `gate` before generating report values.
- Supply an explicit persistence callback receiving the displayed `AnalysisChecksResult`. The report adapter owns selection and commands; it must await transactional receipt saving and committed workspace publication through the existing command boundary. A successful callback alone never fabricates reviewed state.
- The controller owns versioned content fingerprints, current checks, cancellation, bounded caching, completion, saving, and retryable failures. Report-specific result calculation remains outside it and runs only when completion permits it. Never equate `reviewed` with `completed`: clean checks complete with no review receipt.
- Render `AnalysisDataChecksComponent` with checks, findings, and current facility/group labels. It presents one Issues summary with severity totals and a card for each facility/group with issues, combining its affected reporting years and using its highest severity for the card color, followed by an Executive summary across all years, with always-visible comparison tables grouped by reporting year and analysis method. Regression tables show facility/group identity, model year, variable p-values, R², adjusted R², model p-value, formula, and minor issues. Per-row controls and issue links expand the relevant predictor validation table inline without hiding model comparisons.
- Pass the controller's `workflow` to the optional shared header status and `AnalysisChecksAcknowledgmentComponent` in the workbench footer. Handle its typed `acknowledged` output with `confirmReview()`, and use `workflow.completed` for Continue and stage completion. Keep navigation in the workbench. Saving disables duplicate acknowledgment; failure restores the unchecked control; successful keyboard acknowledgment moves focus to the completion message before Continue.
- Better Plants supplies the first adapter. Pending report migrations retain their existing placeholders until they supply their own input/period/command adapter; shared checks do not inspect Better Plants settings or account/facility workbench contexts.

## Better Plants presentation and compatibility

Energy and water reports preserve the current program calculations, selected data, source/site conversions, units, fiscal-year treatment, precision, optional sections, notes, and saved report configuration. The official banner, footer, and form relationships remain, with v1 theme tokens, accessible tables, wrapped notes, and horizontal table overflow at narrow widths.

The in-app preview adds space above the first report and between yearly reports. Facility performance uses a compact table with horizontally and vertically centered cells, adapting to the available width.

Inventory snapshots mark Better Plants content as implemented, so its cards omit the pending-content notice at every detail level. Other report types retain that notice independently of setup readiness.

Two existing presentation/calculation quirks are deliberately characterized rather than corrected in this migration: facility-performance bands use strict inequalities, excluding exact band endpoints; the legacy water participation table places report-year counts in its first numeric column and baseline-year counts in the second. Any correction needs a separate reviewed behavior change and output parity work.

Per maintainer direction, this migration covers setup, checks/review, and in-app display. Printing and file output remain separate work under [#2791](https://github.com/ORNL-AMO/VERIFI/issues/2791) and subsequent output tasks. Existing v0 calculations and writers remain functional; production v1 does not import v0 UI.

Account report and facility Analysis Report-stage footers share `ReportOutputActionsComponent` for the disabled PDF, PowerPoint, and Present placeholders. Shared workbench styles keep the controls wrapped in narrow layouts; navigation and review remain owned by each workbench. Other pending facility reports retain their existing return action.

## Facility Analysis report

The [facility Analysis feature](../src/app/v1/reports/facility/analysis/) composes the existing facility report stages. Setup follows Better Plants: name and report year occupy the top section, followed by the shared analysis cards/filters and a content matrix. Five preset toggles cover facility-only or facility-plus-group Annual Summary and Detail reports, plus Full Analysis with model details. A sixth Custom toggle keeps the current configuration. Presets use separate bordered toggle buttons with single-line labels and visible gaps. Buttons flow onto additional rows when needed without wrapping their labels. Presets patch only content switches; individual edits derive the matching preset or Custom without storing a preset field. Disabled sections retain their table/chart/period choices. Columns and production variables appear inline below the matrix whenever an enabled facility/group section includes a table. Hiding these controls preserves their values. New facility Analysis reports and Reset columns select Actual use, Modeled use, and Adjusted use in Consumption; the three baseline-adjustment columns start unselected but remain available. Existing saved selections and legacy defaults are preserved. Report Setup and the Analysis column picker share presentation-only column options, with report-owned controls and immediate autosave; Analysis retains its separate display preferences and Apply/Cancel behavior. Setup omits the configuration-findings panel while retaining field errors and unavailable/loading states. Typed settings use the shared autosave controller. Partial setup commands reread the latest report and selected facility analysis in one transaction; nested patches preserve untouched options and missing saved links. Missing configuration may be saved, but cannot generate results. Reading or filtering selections performs no writes, pair reconciliation, or active-reporting selection changes.

Direct `FacilityAnalysisReportInputs` carries the selected facility analysis, its owned banking dependency closure, and detached meter/predictor inputs. Shared checks accept either account or direct facility inputs. The direct adapter normalizes review content identically to an equivalent single-facility Better Plants input, preserving existing receipt compatibility. Facility confirmation writes to the facility analysis through the existing transactional review mechanism. Baseline-only report years are supported for facility Analysis; account report period rules remain unchanged. Available periods come from the facility's canonical calendarization and existing full-year helper.

Setup requests freshness only. Data Checks and Report request the selected year's checked model results, including when a current receipt already permits completion, because the report's model details consume those validation results. Historical annual rows and visible monthly/model periods do not expand acknowledgment coverage. Clean checks complete without a write; issues require explicit acknowledgment and blocking or unavailable checks prevent output.

Report results use canonical facility calendarization, the existing facility-results Worker contract, and `calculateFacilityAnalysisResults` with the explicit report year, `calculateAllMonthlyData: false`, and group summaries enabled. The workbench coordinator owns cancellation, retry, the two-minute timeout, and one current result cache. Rendering all sections, scrolling, and changing content visibility do not create another result Worker. Labels reproject from current workspace metadata; changes to calculation-bearing inputs immediately suppress obsolete values.

The Report stage is one continuous document. Enabled sections appear as Facility Annual, Facility Monthly, then each selected-analysis group's Model details, Annual, and Monthly content in analysis order. Every section has its own theme-aware paper block, with the same centered 76rem maximum width and 2rem inter-block spacing as Better Plants. Shared document framing is separate from Better Plants' form table styling. Blocks grow naturally rather than imposing print page heights; the first block contains report identity and period metadata, and every group block repeats its group name. Parent/child switches control visibility; coincident baseline/report/model years produce one monthly table. Disabled sections create no blank blocks, and an empty report links to Setup. The preview has no tab/group-selection state and never persists section navigation. The report and facility/group Analysis screens use the same input-driven [results table renderer](../src/app/v1/shared/analysis-results/results-table/analysis-results-table.component.ts), including grouped headers, theme colors, column highlighting, fiscal-year dividers, rounding, and banking/model markers. Analysis adapters retain column preferences, pagination, and copying; the report adapter supplies its saved columns and bounded periods. Model-detail tables use the same shared table stylesheet. Annual and monthly charts use the same [chart presentation](../src/app/v1/shared/analysis-results/result-charts/analysis-result-charts.component.ts) as facility/group Analysis: annual consumption bars and value labels, monthly comparison shading, stacked savings/loss bars, axes, legends, and responsive spacing. Facility charts aggregate group transition gaps and show total savings; group charts split banking series when their rows are banked. Regression model comparison shares the Analysis scatter/line chart and model-period shading. Report chart actions remain hidden while output work is deferred. Continuous reports opt into viewport-delayed ECharts canvas initialization; headings, tables, and accessible chart data exist immediately. The shared chart boundary defaults to immediate initialization for other consumers, uses the latest option and theme on first visibility, retains initialized charts while scrolling, falls back when viewport observation is unavailable, and disconnects pending observers/disposes charts on exit.

The shared workbench publishes the mounted account or facility report's stage presentation through `ReportStageStateService` using its scope-qualified session identity, clearing it on exit. The sidebar consumes that presentation without creating a checks controller. Report-origin analysis navigation carries explicit facility-report ownership and returns to canonical Setup; existing account return URLs remain compatible.

## Verification

Protect deterministic input selection, review freshness, model checks, form projection, and autosave with fast tests. Cover report runtime retention across stages, teardown on identity changes, pending-format fallback, scope-qualified catalog behavior, and the shared header/sidebar/footer gate. Use Chromium for Worker messages, transaction rollback/stale-review rejection, reopen/backup behavior, and the complete review/display/invalidation journey. Inspect the form at practical desktop and narrow browser widths in light, dark, and high-contrast themes. Follow the [repository validation policy](testing.md) and validation planner for parent checks.
