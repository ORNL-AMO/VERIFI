# V1 Home persistence

The [Home specification](v1-home-dashboard-spec.md) owns the accepted experience. This reference owns the implementing persistence contracts; the [delivery phases](v1-home-dashboard-plan.md) track pending work. UI, runtime reporting resolution, rendering, summary adapters and complete starter recipes remain Home3–Home6 work.

## Records and compatibility

Structural IndexedDB version 22 adds `homeDashboards` and `homeOwners`, each with local numeric keys and GUID/account/facility indexes. Existing stores and records are preserved. Both new stores start empty; startup and hydration never seed templates. Record/payload format 1, saved revision, structural database version and committed workspace revision are separate contracts. Global data version stays unchanged: no existing record needs rewriting. Migration/recovery datasets retain both Home collections, including unknown payloads.

Dashboards have explicit account ownership and optional exact facility ownership. Ownership never derives from linked chart inclusion. Layouts store ordered, independently identified widgets, Half/Full sizes, typed settings, explicit display inheritance/overrides and saved dashboard defaults. Chart widgets contain same-account saved visualization GUIDs. They never embed independent definitions, computed values or browsing state. Notes are plain text; shortcuts use typed internal areas/owner/resource identities rather than arbitrary URLs.

Each store has its own record model/factory and persistence-only repository, following the existing per-store pattern. Their common envelope shares ownership, revision and preservation contracts; application commands retain responsibility for cross-store atomicity.

Owner records retain initialization, saved sidebar order, selected default and deleted starter identities. An initialized empty set is durable intent. Invalid/hidden defaults resolve in saved visible order without hydration writes. Unrelated creation, duplication, adoption, layout edits and deletion retain unavailable owner preferences; explicit owner configuration acknowledges them. Deletion removes only the corresponding verified order/default relationship. Single-facility presentation selects the sole owned facility only for a valid flagged account; portfolios retain account ownership even with one facility. No Home contract creates source data or hidden account analysis pairs.

Template provenance records template/revision, original automatic status, a layout baseline, linked starter-chart revision baselines and sticky customization protection. Unsupported record/payload formats retain opaque JSON and remain unavailable. Envelopes validate identities, revisions, dates and preservation metadata independently of payload decoding. Ordinary supported writes must pass the strict current grammar.

Older backups without Home collections remain supported and prepare empty collections. New Home collections are optional additions to the existing envelope; older releases may omit them on restore, so backward preservation by those releases is not guaranteed. Malformed envelopes, duplicate identities/owner markers and contradictory ownership reject preparation before replacement deletion or writes.

## Commands and workspace

`HomeCommands` prepares stable proposals, captures account/owner identities and expected saved revisions, and submits through `WorkspaceCommandBoundary`. `HomeCommandHandler` validates ownership, revisions, links and full template graphs using only its native transaction context. The transaction includes owner state, layouts and any fresh chart records; one committed workspace reload publishes the complete graph. Home records hydrate into the canonical account snapshot and are read through workspace signals.

Initialization accepts the six symbolic starter recipes but is not called by current navigation. Home6 supplies complete recipes. Matching chart intent shares definitions only within one operation; ordinary creation/restore never deduplicates against existing user charts. Blank creates no charts. Template charts remain ordinary reusable visualizations with Home origin metadata. Explicitly created and duplicated dashboards are always accessible rather than inheriting conditional starter navigation.

Initialization checks the durable marker atomically, including concurrent attempts. Existing imported dashboards without a marker are adopted rather than supplemented. An initialized owner with no dashboards stays empty. Conditional native no-ops do not publish committed revisions or trigger backups; if another writer initialized the owner first, a stale workspace hydrates without reseeding. The presentation helper resolves a valid flagged single-facility account to its sole facility without creating analysis pairs; explicit owner identities remain independent across presentation changes.

Updates save layout/defaults without changing linked definitions or browsing state. Owner configuration includes all current owner-local dashboards and may retain unavailable order entries and an unchanged unavailable default. New defaults must be available; changed preferences or explicit owner `repairPaths` acknowledge only the reviewed relationships. Reordering never verifies a retained blocked preference. Deleting layouts/widgets preserves all linked charts and source records. Default deletion chooses a remaining visible dashboard atomically; hidden/missing defaults otherwise resolve predictably on read without hydration writes. Water eligibility uses a scoped intake/discharge meter's presence, including empty meters; Emissions follows account settings. Explicitly hidden records stay hidden.

Every newly chosen typed widget target must be available in the native transaction. Chart links require a supported valid or setup-required saved record; locked, unsupported, malformed and source-repair records cannot be newly selected or acknowledged as repaired. This does not require source data or calculations to be ready. Unchanged unavailable targets remain editable/duplicable as retained intent, identified by path, resource kind and GUID; switching namespaces never verifies a coincident identity. Explicit repair validates the replacement before clearing its block.

Duplication creates independent layout/widget identities and settings while retaining chart links and blocked source intent. Restore preserves dashboard/local identity, creation date, sidebar/default and visibility choices, allocates fresh charts, preserves former charts and establishes a new baseline. Automatic upgrades require an original automatic starter, untouched layout, exact chart baseline revisions and no unresolved preservation. Saved layout edits and edits/deletion of linked starter charts set sticky protection in the same native transaction, including all shared appearances; returning to old values does not clear it. Owner/source/reporting changes and session exploration do not set that flag. Only explicit restore resets its baseline.

`SavedVisualizationCommands.dependencies` exposes known affected dashboard/widget identities and unreadable-dashboard uncertainty in the existing chart deletion confirmation. `prepareDelete` captures the reviewed dashboard revisions and widget identities; the native transaction rejects changed dependencies even if the chart revision is unchanged. Missing links remain saved, repairable references. A chart mutation returns its complete committed chart and dashboard protection patch together; normal autosaves preserve mounted charts and calculation reuse. Failed patch publication uses the existing committed reload recovery.

Rejected writes retain the proposal and roll back the graph. Conflict recovery hydrates authoritative state without a committed change notification; the caller must prepare a newly reviewed proposal. Publication failure retains a receipt; recovery refreshes committed state without replaying persistence, and resubmitting a recovered receipt acknowledges it without another write. The boundary remembers pending publication per account across owner/account switches. Recovery requires the ready owning account and cannot restore a departed selection. Proposal/receipt storage is session-only, not a durable draft journal.

## Backup, copy and owner deletion

Account backups retain all explicitly owned Home records. Facility export/extraction includes only that facility's layouts and owner marker, independent of chart-derived ownership. Automatic backups serialize the same complete committed workspace snapshot. Facility comparisons include layout/default changes, and import attention summaries include preserved Home formats and unavailable relationships after navigation.

All supported account/facility imports, selected-facility copies and replacements remap the complete graph in the existing native transaction before publication. Charts are transferred first, then layouts, then owner defaults/order. New record GUIDs and local keys are independent; chart sharing within the transferred graph is retained. Resource namespaces use verified source-to-target maps; selected facilities share mappings only within the same source account and operation. Layout notes, widget IDs and unknown JSON are never rewritten by string matching. Chart/layout baselines and Home origin metadata follow verified mappings without clearing customization protection.

Missing chart/resource/owner mappings retain original identity plus durable reference blocks and ordered transfer context. `readHomeWidget` exposes per-widget repair state; later destination GUID collisions or repeated transfers do not verify blocked intent. Layout edits/duplication retain these blocks; explicit repair must select an available same-account replacement or remove the reference. Unavailable saved defaults/order retain raw intent but cannot select a coincident destination dashboard. Explicit owner configuration acknowledges only reviewed valid defaults/order. Unknown formats remain opaque and transfer-locked.

Account deletion removes its Home records. Facility deletion/replacement removes its explicitly owned Home records, including when an older replacement backup omits Home. Surviving layouts retain links to removed facility-derived charts and acquire sticky customization protection in the same transaction. Chart deletion never removes a layout, widget or source record. Restore of a dashboard retains its identity and every former saved chart; backup replacement retains the existing account/facility replacement semantics.

## Reporting bindings

Existing `analysisGuid` targets remain exact. Result sources may instead declare `reporting: { kind: 'reporting', owner: { kind, guid }, category }`, with account/facility owner and energy/water category. Rules cannot also pin an analysis or group. Model sources remain exact. Grouped serialization retains the rule unchanged; runtime resolution and editor support belong to Home4 and no latest-modified fallback is introduced.

Account rules remap only with their owning account; facility rules use the verified facility namespace. Missing mappings remain durably blocked across repeated transfers, even if a destination identity coincides later. The selected reporting analysis is runtime evidence, never a saved substitution for the rule. The existing [visualization persistence contract](v1-visualization-persistence.md) continues to own chart record/deletion/transfer behavior.
